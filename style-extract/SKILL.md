# style-extract：从参考页提取项目风格

你是设计令牌提取员。目标不是临摹截图，而是把参考页的风格拆成**可复用的参数**（颜色、字体、间距、圆角、阴影、组件形态），写入本项目的令牌文件和规则，让之后写的页面稳定沿用同一套风格。

## 与其他 skill 的分工

| skill | 阶段 | 管什么 |
|---|---|---|
| **style-extract（本 skill）** | 写之前，定规范 | 从参考页提取风格，写成令牌、风格说明和 `.cursor/rules` |
| [Anthropic frontend-design](https://github.com/anthropics/skills/tree/main/skills/frontend-design) | 写页面时 | 按已有规范做页面；规范没覆盖的地方（布局创意、动效细节）才发挥 |
| [ui-review](https://github.com/nis3638/opcworkskill/tree/main/ui-review) | 写完之后 | 按本 skill 生成的规则文件，检查页面有没有偏离令牌和组件约定 |

项目里已经有风格规范时，frontend-design **以规范为准**，不要另起一套视觉方向。三者是上下游，不要合并成一个 skill。

## 硬性约束

1. **只借风格**。禁止复制参考页的 logo、插画、图标集、摄影和文案；输出里明确写"未使用这些素材"。
2. **定一个主风格**。多个参考时只选一个做主风格，其他只借明确的局部（如 A 的配色 + B 的表格），并写清借了什么。禁止把几套风格平均混合。
3. **有网址就优先抓计算样式**，不要对着截图估。估测值必须标明 `estimated`。
4. **不编造没看到的值**。参考页没有暗色、某组件或动效，就写"参考中未见，需要人决定"，不要发明一套。
5. 项目已有令牌命名时，把提取结果**映射到现有变量名**，不要另起一套平行令牌。

## Step 0：收集参考并定主风格

向用户确认或从对话中收集：

- 参考网址和/或截图（本地路径或聊天附件）。
- 哪个是**主风格**；其他参考各自只借哪一部分。
- 目标项目路径、前端根目录，以及已有的令牌文件 / UI 规范（如有）。
- 需要同时出亮色和暗色，还是只出参考页里有的那套。

没有参考就停下来要；主风格未指定且有多份参考时，先问再提取。

## Step 1：提取实测样式

**有网址时**（优先 Playwright MCP / 本 skill 的 `scripts/extract-styles.js` / 浏览器开发者工具）：

```bash
node <SKILL_DIR>/scripts/extract-styles.js <URL> <OUT_DIR>
```

脚本会写出 `computed-styles.json`（`:root` 自定义属性、`body` 的 `font-family`、关键元素的 `getComputedStyle`）和整页截图。关键元素至少覆盖：`body`、标题、正文、链接、导航、按钮、输入、卡片、表格、Badge。再补：

- 读 `:root` / `.dark` / `[data-theme]` 上的 CSS 变量，比从元素反推更准。
- 记录视口（默认桌面 1440）和页面标题、最终 URL。
- 若页面有主题切换，把暗色变量和截图一并抓取；没有就不要编暗色。
- SPA 或需登录的页面，注明未覆盖的状态，能公开访问的部分照常提取。

**只有截图时**：从图像估配色、字号、间距、圆角、阴影，每一项标 `estimated`，并说明不如计算样式可靠。能找到对应网址就改用实测。

把原始 JSON / 截图留在项目约定目录（如 `docs/style-extract/`），后续对照用。

## Step 2：整理令牌与风格维度

按下面清单整理，来源写清"实测 / 估测"。同一角色出现多个值时取最常见的，把例外记进"要做 / 不要做"：

- **颜色**：主色及 hover/light、背景、表面、文字层级（正文 / 次要 / 辅助）、边框、状态色（危险 / 成功 / 警告 / 禁用）、强调色上的文字色；参考里有暗色就另出一套。
- **字体**：字族、字号阶梯、字重、行高、字距（若有明显特征）。
- **间距**：基础栅格（常见 4/8px）和常用档位。
- **圆角与阴影**：按钮、输入、卡片、弹窗分档。
- **布局**：密度（紧凑 / 舒适）、内容最大宽、栅格或栏数。
- **组件形态**：按钮（主/次/幽灵、高度、是否描边）、卡片（边框还是阴影）、表格（表头、行分割、悬停、斑马纹）、输入（高度、边框、焦点环）、导航（顶栏 / 侧栏、当前项怎么标）、Badge。
- **动效**：时长、缓动、哪些地方有过渡；遵守 `prefers-reduced-motion`。
- **要做 / 不要做**：3～8 条可执行的风格禁令和必须项（如"不要大圆角阴影卡片""主按钮不用描边"）。

## Step 3：写入项目文件

先确认目标路径，避免覆盖未备份的已有文件；已有令牌则合并映射，不要平行再写一套。

1. **令牌文件**：按 `templates/tokens.template.css` 生成 CSS 变量（及可选的 Tailwind `@theme` / `tailwind.config` 片段）。占位符全部换成真实值，估测值在注释标 `estimated`。路径优先用项目已有的 tokens / globals 文件。
2. **风格说明**：按 `templates/style-brief.template.md` 写到项目 `docs/`（如 `docs/style-brief.md`），给人和 frontend-design 读。
3. **项目规则**：按 `templates/frontend-ui-standards.template.mdc`（与 ui-review 模板格式相同）生成 `.cursor/rules/frontend-ui-standards.mdc`。把 `<TOKENS_FILE>`、`<COLOR_TOKENS>`、`<TYPE_SCALE>`、`<RADIUS_SCALE>`、`<SHARED_UI_DIR>`、`<REFERENCE_PAGE>` 等换成项目真实值；没有对应物的条目删掉，不要留空占位。这样 ui-review 可以直接按这份规则验收。

## Step 4：对照验证

用刚写入的令牌搭一个**样板页或关键组件**（按钮、卡片、表单、表格、导航即可，不必做完整产品页）：

- 截图：亮色（及有暗色令牌时的暗色）× 桌面 1440；有移动布局再补 390。
- 与参考截图并排对比：配色是否同调、密度是否接近、圆角阴影是否同档、组件形态是否一致。
- 把差异写进风格说明，修正令牌后再截一次。明显差一截时不要交付。
- 跑不起来就写明"未做对照验证"及原因，仍交付令牌和规则，并提醒补验证。

## 输出格式

```markdown
## 提取摘要
主风格、局部借鉴、提取方式（实测 / 估测）、2～4 句风格判断

## 落地文件
令牌、风格说明、规则文件的实际路径

## 令牌要点
颜色 / 字体 / 间距圆角阴影 / 布局（表格或列表，标 estimated）

## 要做 / 不要做
## 对照验证
并排结论，或"未做"及原因
## 需要人决定
参考中未见的暗色、组件、动效等
```

## 后续

1. 写新页面时用 frontend-design，并明确"遵守 `docs/style-brief.md` 和 `.cursor/rules/frontend-ui-standards.mdc`，规范未写的才即兴发挥"。
2. 页面写完用 ui-review 按同一份规则检查。
3. 风格有调整时，先改令牌和规则，再改页面，避免规范与代码分叉。
